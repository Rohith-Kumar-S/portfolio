Three retrieval systems, one real catalog. What each one does, how it behaves, and what that behavior reveals.

If you have ever searched an online store for a “cozy living room seat” and received zero results because the database only contained “upholstered armchairs,” you have experienced the fragility of keyword search.

The industry’s answer was vector embeddings — semantic search. But basic semantic search has a blind spot: it captures the vibe of a query while struggling with exact constraints. A search for a “13-inch laptop case” will happily rank a “15-inch laptop case” near the top, because the two descriptions are semantically almost identical.

I built and compared three different retrieval systems for a real retail catalog to see how far each approach gets: an LLM-guided structured search, a retrieve-and-rerank pipeline, and — for the “find similar, but…” experience — a composed image retrieval model. This is what each one does, how they behave, and what that behavior reveals.

A note on the numbers up front. The quantitative results below come from small, hand-judged evaluations (10 queries each). They are indicative, not statistically definitive — treat them as a directional read, not a benchmark. Where a metric has an important caveat (relevance rule, recall blindness), it is stated inline. The most robust number in the whole study is the latency difference.

Approach 1: LLM-Guided Structured Search

The first system uses a language model as a query-understanding front end rather than as the retriever itself.

The pipeline is:

  1. Structured extraction. An LLM reads the raw query and extracts structured fields: product category, subcategory, brand name, and product name.
  2. Attribute-filtered retrieval. Those fields are used to pull candidate products from the database — effectively a hard filter to the extracted category/subcategory (and brand, when present).
  3. Semantic ranking within the category. The remaining candidates are ranked by embedding distance between the query and each product, using nomic-ai/nomic-embed-text-v1.5 for both sides.
  4. Return the ranked products from that category.

The appeal is precision: if the model correctly identifies “this is a dress query,” everything it returns is a dress. The cost, as the evaluation will show, is recall — the system can only ever return what survives the structured filter, and the filter is only as good as the extraction.

What its behavior reveals

In testing, this system frequently returned very few products (as few as one) and occasionally the wrong category entirely. The root cause is architectural: the LLM’s extracted attributes become a hard gate. When the extracted category or subcategory doesn’t line up with how products are actually labeled in the database — asking for “blouse” when the catalog files them under “tops,” for instance — the filter silently excludes valid matches, and recall collapses. When extraction does match the taxonomy, the in-category nomic ranking is quite good. The lesson: an LLM is excellent at understanding a query but a risky choice as the retrieval gate, because a single taxonomy mismatch upstream removes correct products the ranker never even sees.

Approach 2: Retrieve-and-Rerank

The second system separates finding candidates from ordering them — the two-stage funnel used by large-scale search teams.

The “Smoothie” Effect

Basic semantic search relies on a Bi-Encoder: it encodes the query and each product independently into a single dense vector, then compares by distance. The weakness is in how that vector is formed. At the end of the network, the model pools all token vectors into one — averaging them.

Imagine a smoothie: banana, strawberries, and one small piece of chili. Blended, you can tell it’s a fruit smoothie (semantic gist), but the chili’s specific bite is impossible to isolate. In a product description, dominant words like “shoes” and “running” drown out a constraint like “size 10.” The exact detail gets diluted.

Stage 1: The Fast Filter

Because a Bi-Encoder encodes products in isolation, nearly all the work happens offline. Every product in the catalog is embedded once, ahead of time, and the vectors are stored. At query time, only the short query is embedded, and it is scored against the stored vectors with a single matrix multiplication (cosine similarity); the top candidates move on.

At this catalog’s scale (~1,000 products), that brute-force comparison is exact and effectively instantaneous — sub-millisecond on a GPU — so an approximate-nearest-neighbor index such as FAISS is unnecessary. FAISS earns its keep only at hundreds of thousands to millions of vectors, where exhaustive scoring becomes the bottleneck; below that, brute force is both faster and exact, with no index to build or tune. This stage casts a wide net but inevitably lets a few close-but-wrong matches (wrong size or color) through — which is exactly what Stage 2 is for.

Stage 2: The Deep Reader

The top candidates are handed to a Cross-Encoder. Unlike the Bi-Encoder, it uses no pre-computed vectors. It joins query and product into one input:

Because they are processed together, the model runs full self-attention — every query token attends directly to every product token before any pooling. A “size 10” in the query looks straight at a “size 11” in the description and sees the clash instead of averaging it away, so it can penalize the mismatch. This depth is also why the rerank stage dominates the pipeline’s latency: it runs a full transformer over each candidate pair. Precision has a price.

Training: Hard Negative Mining

A Cross-Encoder doesn’t know your specific catalog out of the box. It is trained on triplets:

  1. the query,
  2. the true product, and
  3. a hard negative — the product that most convincingly fooled the Bi-Encoder.

A pairwise margin loss forces the true product above the hard negative:

Loss = max(0,  Scoreneg − Scorepos + Margin)

Penalizing the model whenever it ranks the impostor above the real match teaches its attention heads to act like a spotlight — hunting the specific constraints (size, color, brand, model number) that the Bi-Encoder blends away.

What its behavior reveals

This system retrieved a full candidate set on every query and ranked it cleanly. Because Stage 1 casts a wide semantic net rather than a hard attribute gate, it keeps recall high; because Stage 2 reads query and product jointly, it orders precisely. The contrast with Approach 1 is the whole story: soft-retrieve-then-rerank preserves the candidates that a hard structured filter would have discarded.

Two things the data shows:

  1. Ranking is comparable when both return results — recall is not. The LLM system’s MRR of 0.80 means that when it surfaces the right category, it usually ranks it near the top; its nomic-based in-category ordering is genuinely good. Its problem is upstream: the structured filter under-retrieves, returning as few as one product and occasionally missing the category outright. The retrieve-rerank system’s high, retrieved-normalized NDCG combined with a full 20-result list is the point — it ranks well and covers the catalog. Note that the retrieved-normalized metric actually understates this gap, since it gives the LLM system no penalty for its thin result lists.
  2. The generative latency tax is real. The ~5.3-second LLM path (dominated by the extraction call) versus ~477 ms is the study’s most robust finding: an ~11× difference that no amount of sampling noise will erase. For an interactive search bar, that alone is decisive.
Caveats to carry: n = 10 (indicative, not definitive); the NDCG figure depends on loose, category-level relevance judgments (a few borderline calls shift it); and it measures ranking of retrieved results, not recall — which is why the retrieval-count row is reported alongside it.

Stage 3: Composed Image Retrieval for “Similar Products”

Text search answers “find me a blue floral dress.” It cannot answer the request a shopper makes while looking at a product: “this dress — but in navy, with long sleeves.” That is a reference image plus a modification, a distinct task called Composed Image Retrieval (CIR), and it is what powers a true “find similar, but…” button on a product page.

I built this as a separate system: a CLIP ViT-B/16 backbone with a FiLM-based combiner that fuses the reference image embedding with the text-edit embedding, fine-tuned with LoRA on the FashionIQ dataset. At query time, the reference product and the edit are encoded and combined into a single query vector, then ranked by dot product against the pre-embedded catalog.

This is a different task from text search and is not directly comparable to it. The relevance bar is higher: a result counts only if it preserves the reference’s garment type and applies the requested edit. A “navy dress” is a failure for a “navy tunic” query.

On a 10-query in-domain evaluation using the strict rule above (category preserved and edit applied), the system reached ≈ 0.84 NDCG@5 and ≈ 0.85 MRR. This uses a stricter relevance rule and a different task than the text-search comparison — the two numbers should not be placed on the same leaderboard.

What its behavior reveals

Two clean inferences. First, the model is strongest on color and pattern and weakest on sleeve length and compound edits — the FiLM combiner learned to modulate global appearance attributes (color, texture) more readily than structural ones, and stacking two edits divides its capacity. Second, its two failure modes trace to data and architecture, not the fusion mechanism: it drifts on out-of-domain categories because FashionIQ contains only dresses, shirts, and tops (there is no training signal for pants or home goods), and it ignores position because CLIP’s Vision Transformer lacks the spatial inductive bias that left/right edits require. Within its trained attribute-and-category envelope, composed retrieval works well.

Future Work: Teaching the Model Where

The clearest next step is the positional-edit gap. CLIP embeddings are notoriously weak at spatial relations, and no amount of attribute fine-tuning installs a capability the backbone never had. A promising direction is to inject CNN-style spatial inductive bias — applying the text modification at the convolutional feature-map level, where layout is preserved, rather than at the pooled embedding. Prior work (TIRG) found that this specifically helps on spatially-localized retrieval. The blocker is data: no positional-edit fashion dataset exists publicly, so this would require synthesizing one (e.g. compositing features at known positions with generated captions) before the architecture could learn anything. It is a research direction, not a quick add-on — but it is the honest frontier for this system.

Takeaways

Three systems, three lessons:

  • An LLM is a strong query understander but a weak retrieval gate. Structured extraction plus a hard category filter buys precision at a steep recall cost, and it inherits every taxonomy mismatch as a silent miss.
  • Retrieve-and-rerank wins by not throwing candidates away. A wide semantic net (Stage 1) plus token-level joint reading (Stage 2) delivers both coverage and ordering — an order of magnitude faster than the generative loop, on this catalog.
  • Composed retrieval unlocks an interaction text can’t express, and it works well within the attributes and categories it was trained on. Its limits — out-of-domain drift, no spatial reasoning — are traceable and, in principle, fixable with the right data.

Search stops being a matching game and starts becoming contextual reasoning the moment you stop asking one model to do everything, and instead let each stage do the one thing it is actually good at.
